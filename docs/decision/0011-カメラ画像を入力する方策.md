# 0011 カメラ画像を入力する方策（A 案: 関節角 + 画像）

- ステータス: 実装済み・本番の収録／学習／評価は未実施
- 日付: 2026-10-16

## コンテキスト
これまでの方策（ACT）の入力は、関節角と数値の物体位置・置き場所だった。
物体位置は真値（ADR 0005）か、カメラ画像からの検出器（赤色検出・RT-DETRv2, ADR 0008 / 0009）で得て、方策には画像を入れていない。
課題の発展として、方策に画像を直接入力できないかとユーザーから相談があった。

- 俯瞰カメラ（`/task/camera/image`、320×240、10Hz、真下向き）はすでにあり、検出器が使っている
- 同梱の LeRobot の ACT は `observation.images.*` を定義すると、ImageNet 学習済みの ResNet18 で画像を読む（モデルのコードは変えなくてよい）
- これまでの rosbag には画像が入っていない

## 検討
- **A 案: 関節角 + 画像（物体位置・置き場所なし）**: 物体と置き場所の位置を方策が画像から読む end-to-end の形。
  検出器 → 数値の物体位置という今の構成と比べやすい
- B 案: 関節角 + 画像 + 物体位置・置き場所: 画像を補助として足す。安定しやすいが、何が効いたのかを説明しにくい

## 決定
A 案を採る（2026-10-16 ユーザー決定）。

- データ: 最終モデル A' と同じ条件（置き場所ランダム、固定開始 200 ＋ 開始姿勢ばらつき 200、seed 1200 / 1201）で、
  カメラ画像を加えて収録し直す（`recorder_image.yaml`、録画先 `~/dataset/rosbags/pick_place_image`）
- 変換: 変換設定に `observation.images: [<カメラ名>]` と `topics.<カメラ名>` を追加し、`environment_state` は空にできるようにした。
  画像は 20fps の各フレームで直前の画像を使う（カメラは 10Hz なので 2 フレームずつ同じ画像）。
  全エピソードの画像をメモリに載せると数 GB になるため、1 回目は時刻だけを集め、書き込み時にエピソードごとに読み直す
- 学習: A' と同じ 80k step・batch 32・chunk 16。画像の backbone だけ学習率を 1e-5 にする（ACT 論文・LeRobot の既定。画像なしのモデルは今までどおり）
- 推論: 変換設定の画像トピックを購読し、学習時と同じ (3, H, W) float [0, 1] にして渡す
- 画像の拡張（色・位置のランダム化）は最初は入れない。見た目ランダム化での評価で弱ければ検討する

## 懸念
- 運搬中は物体がグリッパに隠れる。A' では物体位置を固定して対処したが、画像の方策は関節角と画像から直接学ぶので固定はしない
- 学習は画像のデコードと ResNet の分だけ重い。収録データも 1 本あたり数十 MB と大きい
- 物体の位置を数 mm の精度で読めるかがわからない（A' の失敗は「狙いが数 mm ずれる」ものだった）
